# 偶发失败：重复运行、保留完整日志、用统计证明修好

不要靠"重跑一次变绿"来修好偶发失败：先抓到根因，再用足够多次的重复运行证明它没了。

## 1. 认出症状

日志里**所有测试都通过**，最后却多一行 `Errors N error` / `Unhandled errors`，整体退出码非 0。这几乎总是**测试结束、环境被销毁之后才触发**的异步（没清理的定时器、回调、订阅）；机器越忙越容易撞上。

## 2. 量频率并保留证据

用 `${CLAUDE_PLUGIN_ROOT}/skills/flaky-test-hunt/templates/repeat-tests.yml`，在一台**空闲**的 runner 上**原样**重复运行 CI 的测试命令 N 次（≥ 7）：

- 每一轮完整输出写文件（不要只留 tail，runner 清理后就没了），失败时在步骤日志里打印失败测试和错误栈，并上传失败轮次的日志；
- 记录每轮耗时和前后负载；
- 循环里必须 `set +e`，否则 GitHub 默认的 `bash -e` 会在第一个失败时直接退出，后面的轮次全丢。

## 3. 读错误栈：谁在测试结束后还活着

`Unhandled Errors` 栈的最底下通常就是触发源（如某组件的 `setTimeout` 回调）。问：
1. 组件/对象**卸载或销毁时有没有清理**？
2. 有没有"挂了新的没清旧的"？（两个事件处理函数先后触发，后一次覆盖保存定时器编号的引用，前一个永远清不掉。）
3. 触发它的已有测试是不是"只验证不报错就结束"，留下挂起的异步？

## 4. 修复要有不依赖真实时间的确定性测试

用假定时器断言**"不遗留"**：
```
测试 1：触发调度 -> 卸载 -> 断言挂起的定时器数量回到基线
测试 2：先后触发两次调度 -> 只保留最新一个，卸载后归零
测试 3：原有行为不变（到点后确实执行）
```
先让测试**因为正确的原因变红**（如 `expected 1 to be 0`），再改代码变绿；然后**故障注入**：分别去掉修复的每一半，对应测试应变红。

## 5. 用统计证明修好

在修复分支上用同一模板再跑 N 次。若原失败率是 p，修复无效却 N 次全过的概率是 (1-p)^N：p=25% 时 N=7 约 13%，N=10 约 6%。所以 10 次 0 失败是**强证据而不是证明**，样本小要写明。

## 6. 复现不了就别提"修复"

可以在本机用满载进程重复运行单个测试几十次。仍复现不了，就如实记成"观察到 1 次，疑似原因 X，未复现"；想做防御性改动，PR 里也只能写成"缓解疑似问题，未验证"。
