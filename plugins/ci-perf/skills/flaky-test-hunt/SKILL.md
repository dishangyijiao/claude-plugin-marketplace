# 偶发失败：重复运行、保留完整日志、用统计证明修好

**不要靠重跑一次变绿来"修好"偶发失败。** 要先抓到根因，再用足够多次的重复运行证明它没了。

## 1. 先认出症状

- 日志里**所有测试都通过**，最后却多一行 `Errors N error` / `Unhandled errors`，整体退出码非 0。这类几乎总是**测试结束、测试环境被销毁之后才触发**的异步代码（没清理的定时器、回调、订阅）。
- 同一个提交，一次绿一次红。
- 只在机器忙的时候出现（负载大 → 异步间隔变长 → 竞态更容易撞上）。

## 2. 量出频率，并保留证据

用 `templates/repeat-tests.yml`：在一台**空闲**的 runner 上，**原样**重复运行 CI 里的测试命令 N 次（建议 ≥ 7），每一轮：

- 完整输出写进日志文件（**不要只留 tail**，runner 清理后就没了）；
- 失败时直接在步骤日志里打印失败的测试名和错误栈，并把失败轮次的日志上传成 artifact；
- 记录每轮耗时和前后系统负载，用来看和负载是否相关；
- 循环里必须 `set +e`，否则 GitHub 默认的 `bash -e` 会在第一个失败时直接退出，后面的轮次全丢。

## 3. 读错误栈，找"谁在测试结束之后还活着"

看 `Unhandled Errors` 那一节的栈，最底下通常就是触发源（比如某个组件里的 `setTimeout` 回调）。接着问：

1. 这个异步是谁创建的？组件/对象**卸载或销毁时有没有清理**？
2. 有没有"创建了新的但没清掉旧的"（例如两个事件处理函数先后触发，后一次覆盖了保存定时器编号的引用，前一个就永远清不掉）？
3. 触发它的已有测试是不是"只验证不报错就结束"，留下了挂起的异步？

## 4. 修复要有确定性的测试，不依赖真实时间

用假定时器断言**"不遗留"**，而不是等真实时间碰运气：

```
测试 1：触发调度 -> 卸载 -> 断言挂起的定时器数量回到基线
测试 2：先后触发两次调度 -> 断言只保留最新一个（不叠加），卸载后归零
测试 3：原有行为不变（到点后确实执行）
```

先写测试看它**因为正确的原因变红**（例如 `expected 1 to be 0`），再改代码变绿；然后**故障注入**：分别去掉修复的每一半，对应的测试应该变红，证明测试真的守着这两处。

## 5. 用统计证明修好

在修复分支上用同一个模板再跑 N 次。若原失败率是 p，修复无效时 N 次全过的概率是 (1-p)^N：

| 原失败率 | N | 修复无效却全过的概率 |
|---|---|---|
| 25% | 7 | 约 13% |
| 25% | 10 | 约 6% |

所以 10 次 0 失败是**强证据**，不是证明；样本小的时候写明这一点。

## 6. 复现不了时怎么办

- 在本机用一批满载进程制造高负载，重复运行单个测试几十次。
- **仍然复现不了，就不要提改动。** 把它如实记成"观察到 1 次，疑似原因是 X，未复现"，等再次出现时有更多证据再处理。一个无法证明的"修复"只是补丁。
